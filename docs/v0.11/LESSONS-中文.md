# 这次修复的经验总结

## 1. 先查当前交付物，再判断原因

“看起来无敌”不能直接等于代码里有永久无敌。核对当前源码、发行预设和真实伤害记录后，v0.7普通僵尸潮确实掉血。普通受击缓冲、翻滚/冲撞、初级自动回血、地面回血与开发测试的持续恢复生命，都可能让观察产生不同印象。修复应该把这些机制分开，而不是随手删除一个并不存在的开关。

本次把新增护盾单独作为状态，伤害函数统一读取状态，保留原有短暂受击保护。测试明确检查拾取前、拾取中、结束后，避免用开无敌的机器人证明游戏能正常受伤。

## 2. 临时能力的边界比时长更重要

“5秒无敌”必须同时定义暂停、慢动作、重复拾取、死亡、结局和重开。这里按未暂停实际时间计时；暂停冻结，慢动作不无限延长，生效时拒绝刷新与叠加，死亡/结局清空，新玩家从零开始。掉落稀疏、地面最多一件并有限寿命，避免一堆道具累积后变成实质永久保护。

视觉与状态来自同一倒计时：脚下蓝色光环、HUD精确数字、最后一秒警告与结束提示。声音不可用或被静音时，玩家仍能看清保护何时结束。

## 3. Web声音不是把音量推到0dB

音频有多层：源文件内容→资源导入→实际播放器触发→总线音量/静音→Web播放模式→AudioContext状态→浏览器用户手势→系统输出。有效波形只证明文件有声音；播放器playing只证明引擎发出播放请求。

先保留原有SFX/Music设置和混音，再解决初始化、手势恢复、拒绝重试和状态可见性。不要通过强制取消总线静音或播放静音循环去掩盖未知原因，也不要忽略resume Promise的失败。引擎的播放器Stream枚举和项目默认播放模式枚举不是同一编号，必须核对。

## 4. 首次手势不能顺手损坏操作

音频观察监听只负责恢复声音，不preventDefault，不拦截touchmove/dblclick，不伪造点击，也不吞掉第一次真实游戏操作。初始化和手势恢复的时序需要单独检查；失败后下次合法手势可以重试，不留下多个监听器或无限播放的辅助音频。

## 5. 原生、逻辑模拟和真机证据必须分开

实际游戏类的回归能证明伤害与计时；原生渲染能证明布局与反馈；JavaScript模拟能证明Promise/retry分支。它们都不能代替真实手机听感、浏览器音频输出、系统手势或GPU性能验证。

本包明确注明已测与未测，保留可复现命令、日志与实际运行截图。引擎和模板完全匹配；源码保持4.5工程声明，导出使用的4.6.3版本另行说明，不把无提示迁移当成修复。


## 6. 同一试玩地址不一定是同一版文件

先核对实际加载的HTML脚本与构建指纹，再判断新修改是否生效。此次旧试玩地址显示历史音频桥接和旧资源大小，不能用它证明当前完整构建的声音结果。新版应整目录上传，避免组件混版。

AudioContext running只是第一层。Stream音频还需要worklet模块加载、节点连接与有效PCM；4.6.3的异步worklet失败不会自动回退。源码/故障注入可以证明这条风险边界，只有实际浏览器请求/输出才能把它认定为某个网址的具体根因。没有这层证据时，保持边界并提供版本/音频诊断，别再盲目加音量或宣称修好。
